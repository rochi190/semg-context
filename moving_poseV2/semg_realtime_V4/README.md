# sEMG 即時分類（可獨立下載執行）

STM32 + ADS1299 → 7 通道 sEMG → 三個自由度的即時分類。
**這一包是自足的**，不需要整個 repo。

```
check_install.py    不接板子也能跑，確認套件、模型、電極對照
list_ports.py       找出板子接在哪個埠
run_live.py         即時分類（單一模型）
run_compare.py      ★ 兩個架構並排比較（吃同一條資料流）

models/             3 個訓練好的模型（兩種架構）
src/semg/v2/        pipeline（config / preprocess / features / cues /
                    model / infer / live）
src/hardware/
  record_session.py 錄製 + 同步 cue（序列埠解幀的正本）
requirements.txt
```

⚠️ 所有腳本自己會把 `src/` 加進 `sys.path`，**不需要設 `PYTHONPATH`**
（Windows 的 cmd 沒有 `PYTHONPATH=src python ...` 這種寫法）。
Windows / Linux / Mac 指令完全相同，只有埠名不同（`COM3` vs `/dev/ttyUSB0`）。

## 三個模型（v4）

| 檔名 | 架構 | 參數 | **沒見過的組合** | 一般 LORO |
|---|---|---|---|---|
| `final_v4_split` **(預設)** | 分離編碼器 | 17,776 | **85.4% ± 1.9%** | 87.9% |
| `final_v4_tiny` | 共享 backbone | 11,916 | 5.0% ± 2.0% | 86.4% |
| `final_v4_zhao` | CNN+BiLSTM+Attn | 355,913 | 0.2% | — |

★ **換檔名就換架構**，不用改任何設定（架構名記在 `.pt` 的 `arch` 欄位）。

### v4 相對 v3 改了什麼

v3 接上板子實測時發現：**舉 elbow + index 時 hand 不觸發** ——
模型做不出訓練時沒 cue 過的組合（16 種只 cue 過 9 種）。

根因**不是**資料覆蓋，也不只是特徵，而是**共享 backbone 把「哪些自由度會同時
出現」學進了表示層**。決定性的證據（訓練時排除 pinch+彎肘，測能否自己組合）：

| 特徵子集 | hand | elbow |
|---|---|---|
| 全部 120 維 | 66.7% | **29.9%** |
| 只有近端 60 維 | 0.0% | **91.8%** |
| 只有遠端 45 維 | **89.1%** | 0.5% |

另一組的特徵不是沒幫助，是在**主動干擾**。所以 `split` 把編碼器拆開：

```
遠端 3 通道（曲腕/食指/拇指）    → distal   編碼器(51維) → hand 頭
近端 4 通道（背闊/二頭/三頭/三角）→ proximal 編碼器(66維) → elbow 頭
                                                        → shoulder 頭
跨組的 3 維（grp_*、logr_distal_proximal）兩邊都不給   ← 耦合來源
```

手部頭**物理上看不到手臂的任何資訊**，所以「捏住+彎肘」對它而言跟
「單純捏住」是完全相同的輸入 —— 不需要見過那個組合。

多種子驗證：**5.0% ± 2.0% → 85.4% ± 1.9%**，3/3 種子，配對 t **p=0.0008**。

⚠️ **代價是真的**：一般 LORO（組合都見過）上六份錄音**全部小幅變差 0.8–3.8pp**。
即時操作本來就會做沒 cue 過的動作，所以預設用 split，但三個模型都在包裡。

⚠️ **v4 模型不能配 v3 程式，反之亦然。** `prop_` 特徵的定義變了（分母從全通道
改成組內），維度仍是 120 —— 混用**不會報錯**，只會準確率莫名其妙差。
模型檔記了 `feat_version`，載入時不符會直接拒絕。

### ★ 移動過程的誤判：`--dwell`

v3 實測回報「動 index 時移動過程會標出 pinch，回 rest 也會」。
根因是協定把 `prepare` / `return` **整段丟棄**，模型從沒見過移動過程。

`--dwell N`：候選新狀態要**連續出現 N 次**才換。
⚠️ **投票對付抖動，遲滯對付轉換期** —— 「穩定地標錯」不是抖動，投票擋不住。

| 誤判持續 | dwell=0 | dwell=6 | dwell=10 |
|---|---|---|---|
| 250 ms | 誤判 250 ms | **0** | 0 |
| 400 ms | 誤判 400 ms | 400 ms | **0** |
| 600 ms | 誤判 600 ms | 600 ms | 600 ms |

**只擋得掉比它短的誤判**，而且正確狀態也會延遲同樣時間。建議先試 6。

## 2. 執行

```bash
# ★ 靜止誤觸發測試 —— 接機械手臂前**必須先做這個**
python run_live.py COM3 --idle-test 60

# 一般即時分類
python run_live.py COM3

# 換 zhao 架構
python run_live.py COM3 --model final_v4_zhao

# ★★ 兩個架構並排比較（見 §5）
python run_compare.py COM3 --idle-test 60

# 沒有板子時：用錄好的檔案模擬序列埠
python run_live.py --replay 某份錄音.csv --replay-fast
```

Linux 把 `COM3` 換成 `/dev/ttyUSB0`。

★ **`run_live.py` 也可以直接驅動 UFACTORY Lite 6**（2026-08-19 整併）：加
`--arm-ip <IP>` 或 `--arm-dry-run` 即可，其餘用法完全相同。這需要完整的
`moving_poseV2/`（控制層在 `../src/control/`）——單獨下載這一包時只有純螢幕模式。
指令、參數與完整驗證流程見 `../docs/control-commands.md`。

★ **換模型就換架構，不用改任何設定** —— 架構名稱記在 `.pt` 的 `arch` 欄位，
載入時查 `model.ARCHITECTURES` 自動建對應的網路。

開機會要你**靜止 5 秒**做校準 + 電極自檢。

### 電極自檢怎麼看

看每個通道**濾波後**的靜止基線：

| 基線 | 判定 |
|---|---|
| 1–5 µV | 正常 |
| > 15 µV | ⚠️ 偏高（接觸阻抗或環境干擾） |
| > 40 µV | ❌ 重貼 |

⚠️ **直流偏移那一欄不是問題**，帶通會濾掉。曾經有人（我）拿原始訊號的
絕對門檻當「飽和率」，把一個完全健康的通道判成全毀 —— 要看的是濾波後那一欄。

這 10 秒是目前投報率最高的一件事：實測它在**錄製前**就抓得到後來造成問題的
兩片電極（46.6 µV 與 318.0 µV，乾淨的只有 1–5 µV）。

### 其他參數

```bash
--votes 5        投票票數（大 → 穩但延遲高）
--conf 0.6       信心門檻
--calib-sec 5    校準秒數
--replay <csv>   用錄好的檔案模擬序列埠（沒有板子時測程式用）
```

## 3. 目前的效能（誠實版本）

| | |
|---|---|
| 預設模型 | `models/final_v4_split.pt`（7 份錄音訓練） |
| **一般情況** | **≈ 87.9%** 三個自由度同時正確 |
| **沒見過的組合** | **≈ 85.4%**（v3 只有 5%） |
| 逐 DOF 平衡準確率 | hand 94.8 / elbow 91.4 / shoulder 95.9 |
| 基準線（永遠猜 rest） | ≈ 26% |

87.9% 是**留一份錄音**的交叉驗證平均 —— 每次都用其他錄音訓練、對沒看過的
那一份做串流推論，所以它回答的是「**換一天、換一次貼片，還能不能用**」。
模型本身沒有自己的準確率（全部資料都拿去訓練了），87.9% 是誠實的引用方式。

另一個模型 `final_v4_tiny.pt` 多含一份需要遮蔽 41% 的錄音，
期望值 ≈ 88.7%、變異較大。要換加 `--model final_v4_tiny`。

### 延遲

**1.15 秒**，組成是：視窗 0.50 + 序列脈絡 0.45 + 投票 0.20。

這是**設計值不是效能問題** —— 實際計算只花 **6.4 ms**（中位；v3 是 17.9 ms —— v4 拿掉了 Hampel 濾波，多種子確認準確率無顯著差異 p=0.926）。
要降延遲只能動這三個參數，優化程式沒用。

⚠️ 計算耗時偶爾會衝到 **60–65 ms，超過 50 ms 的步進預算**。
中位數只用掉預算的 **13%**（v3 是 36%）；但筆電同時跑序列埠讀取與手臂控制時要留意。

## 4. 切窗方式

**逐樣本推進的滑動窗，不是一塊一塊切。**

```
序列埠 ── 每 100 樣本(50ms) 一塊
   ↓
StreamFilter        60Hz notch → 20–450Hz 帶通 → 因果 Hampel(K=201)
   ↓                濾波器狀態跨塊接續（因果，不能看未來）
deque(maxlen=1000)  逐樣本 append 的 0.5 秒滑動窗
   ↓                每滿 100 樣本吐一個窗 → 重疊 90%
features.extract    1000×7 → 120 維
   ↓                (x − mean)/std，用訓練時存下的 scaler
deque(maxlen=10)    堆 10 個特徵向量 = 0.95 秒脈絡
   ↓
model(1,10,120) → 3 個 softmax 頭
   ↓
MultiVoter          每個 DOF **各自** 5 票多數決 + 信心 ≥ 0.6
```

| 參數 | 值 |
|---|---|
| 視窗 | 1000 樣本 = 0.5 s |
| 步進 | 100 樣本 = 50 ms（每秒 20 個預測） |
| 重疊 | 90% |
| 序列脈絡 | 10 個窗 = 0.95 s |

投票是逐 DOF 的：肩膀在抖不會拖累食指的輸出。

## 5. ⚠️ 還沒量到的數字，也是接手臂前的關卡

**靜止時的誤觸發率。**

目前所有準確率都來自照腳本做的 cue 錄音 —— 那裡的 rest 是「被要求休息」的 rest。
真實使用時人會抓癢、調整姿勢、隨意動，那種情況下會不會誤觸發，
**在任何離線資料上都量不到**。

```bash
python run_live.py COM3 --idle-test 60      # 完全不動 60 秒
```

⚠️ **不要對 `--replay` 的檔案做這個測試。** cue 錄音裡受試者一直在動，
算出來的「誤觸發率」其實是「模型正確偵測到動作的比例」，沒有意義
（實測過一次 49.88%，差點被當真）。程式現在會警告，但還是提一下。

手部 DOF 誤判只是夾爪亂開合；但 elbow / shoulder 誤判會讓**真的機械手臂動起來**。
所以順序是：

1. `--idle-test 60` 看誤觸發率
2. 可接受 → 自由動作的即時分類，對照螢幕看手感
3. 都 OK → 才接 Lite 6，並且加 enable/deadman 閘門

誤觸發率如果偏高，最直接的方向是加大 `--votes` 或拉高 `--conf`，代價是延遲增加。

### ★ 兩個架構怎麼比才有意義

```bash
python run_compare.py COM3 --idle-test 60
```

**兩個模型吃同一條資料流**，濾波與特徵只算一次（省掉重複計算），
所以兩者看到的輸入**逐位元相同**，差異一定來自模型本身。

⚠️ **絕對不要分兩次跑再比。** session 與貼片的變異遠大於架構差異：
實測同一間教室、相隔 12 分鐘的兩份錄音差 **62.7% vs 97.0%**，
而兩個架構的離線差異只有 1~2pp。分兩次比出來的是「哪次貼得比較好」。

會輸出三組數字，但**只有一組能當準確率用**：

| 輸出 | 能不能當準確率 |
|---|---|
| 各 DOF 的狀態分布 | ❌ 只是分布，沒有真值 |
| 兩模型**一致率** | ❌ 一致不代表都對，可能一起錯 |
| **靜止誤觸發率**（`--idle-test`） | ✅ **唯一有真值的** |

★ `--idle-test` 之所以是唯一有意義的比較：**人靜止時沒有意圖，
所以任何非 rest 的輸出一定是錯的**。即時流沒有 cue，其他情況都沒有真值。

離線的準確率比較請看 `results/arch_zhao/`（不在這一包裡），
結論是 3 個種子下 **p=0.051、不顯著**。

## 6. 這一包也能錄音

`src/hardware/record_session.py` 是完整的錄製程式（V3 協定），
包含在這裡是因為序列埠解幀邏輯是共用的 —— 即時分類直接 import 它的
`find_sync` / `read_one_frame`，避免兩份實作走樣。

```bash
python src/hardware/record_session.py --list-ports
python src/hardware/record_session.py --port COM3 --probe
python src/hardware/record_session.py --dry-run --subject gary   # 不接板子看時序
python src/hardware/record_session.py --port COM3 --subject gary
```

⚠️ 錄音時的電極位置**照本檔 §1 的表**，不要照 V3moving 的（那份是舊的對應）。
