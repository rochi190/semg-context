### 2.2 📌 JP21 / JP22 是什麼（TI 文件沒寫，從原理圖反查）

SLAU443B Table 1「Factory Default Jumper Settings」在 JP21 與 JP22 這兩列的
**Comment 欄位是空白的**（TI 漏填）。功能要看第 53 頁
**Figure 62「ECG MDK Board Interface Adapter」**：

- **JP21 → `SPI_CS`** 的路由選擇（三腳跳線）
- **JP22 → `SPI_START`** 的路由選擇（三腳跳線）

兩者決定 CS / START 訊號從 MDK 母板連接器來、還是走另一路徑。

> 這解釋了 `ads1299.c` 裡那句註解：
> 「如果硬體 START 被強制覆寫或 **JP22 錯誤**，導致暫存器沒吃進去」——
> START 若被外部拉高，ADC 持續轉換，暫存器寫入權限被鎖，
> readback 就會對不上。JP22 設錯的症狀正是「ID 讀得到但暫存器寫不進去」。

### 2.4 ⚠️ ch2 / ch4 衝突 —— 已確認，且修正會使模型失效

**實體貼法確認為：ch2 = 二頭肌、ch4 = 三角肌前束**，與 `config.py` **相反**。

**修法：改 `config.py`，不要動電極線。**
動線材會讓已錄的 4–5 份資料與新資料通道順序不一致，等於全部作廢；
改名字則完全不影響已錄資料（通道順序未變，只是標籤正確了）。

```python
# 修正後

            "wrist_flexor", "index", "thumb")
```

**⚠️ 後果：`dof_model.pt` 必須重訓。**
`CROSS_PAIRS` 是用**名字**去查通道索引的，改名會改變實際相除的通道：

| `CROSS_PAIRS` 項目 | 修正前實際算的 | 修正後 |
|---|---|---|
| `("biceps", "triceps")` | ch4 ÷ ch3 = 三角肌前束 ÷ 三頭肌（跨兩關節，無拮抗意義） | ch2 ÷ ch3 = 二頭肌 ÷ 三頭肌 ✅ |

特徵向量的值改變 → 舊模型不適用。

**建議當成一個 30 分鐘的對照實驗**：改名 → 重訓 → 比較準確率。
修正後的配對在生理上才真是拮抗對，有機會變好；若反而變差就保留舊版，
但海報上必須說明 `CROSS_PAIRS` 的命名與實體不符。
**務必排在 freeze 日之前完成。**

### 3.2 準確率

- **指標是 per-head 平均準確率**（三個 head 各自算再平均），
  **不是全對率**（三個 head 全對才算對）
- 多數檔案接近 99%，**1–2 份約 70%**
- 70% 的檔案歸因為「線材被拉到」，使用者認為可避免、也可重錄
- confusion matrix 看過，**錯誤不集中**在特定類別

### 3.3 ⚠️ 三個必須寫進海報的誠實聲明

**① per-head 準確率 ≠ 使用者體驗到的準確率**

三個 head 各自 95% → 全對率僅 `0.95³ ≈ 86%`。
**海報必須註明報的是哪一種**，建議兩個都報：per-head 拆開列
（讀者看得出哪個 DOF 難）+ 全對率（這才是實際操作時的體驗）。

**② n = 2 撐不起泛化宣稱**

leave-one-file-out 的驗證方式本身正確（遠優於同檔內隨機切，
因為相鄰視窗有 450 ms 重疊，同檔隨機切會嚴重高估）。
但 2 位受試者不能寫「泛化性良好」，應寫
**「在 2 位受試者上驗證，跨受試者泛化未評估」** ——
誠實反而擋掉一個必被問倒的問題。

**③ `CUE_SHUFFLE = False` 的殘留效應**

固定順序使前一個姿勢的殘留**系統性**混入。這是已知的 limitation，
必須主動列出，不要等被問。

### 3.4 ⚠️「線材拉到」這個歸因值得驗證

管線裡有 causal Hampel filter（half-window 100 samples, σ=2.0），
**它本來就是設計來吃掉這類 spike 的**。若一次拉扯能讓準確率掉到 70%，
代表發生的可能不是 spike，而是：

- **持續性基線偏移或阻抗改變** → Hampel 對此無效
- **或者根本是 UART 掉包**（見 §5.2），症狀是「波形看起來正常但標籤錯位」

兩者的處置完全不同：spike 偶發、重錄可避開；
基線偏移代表電極貼附或線材固定方式有**系統性**問題，重錄還會再發生。

👉 **驗證方式**：把 70% 那份檔案畫出來，看異常是**尖峰**還是**台階**。20 分鐘。

> 開關跳過那幾行 —— 但那要改程式碼，比裝夾爪麻煩。

### 5.2 順手做完的兩個零成本檢查（接上 STM32 時）

**① overrun counter**

正常跑 30 秒後，用 Live Expressions 看：

### 5.3 上機順序（不要跳步）

```
1. --source mock --dry-run          假手勢 + 假手臂，純驗狀態機（不需硬體）
2. --source mock --arm-ip ...       假手勢 + 真手臂  ★ 第一次接手臂用這個
3. --source replay --csv ... --arm-ip ...   真模型重播 → 真手臂
4. --source live --port COM10 --model ... --arm-ip ...   最終部署
```

**為什麼不能跳到 4**：`mock` 是腳本化的假分類器（20 Hz 吐固定腳本），
輸入已知且完美。手臂不照腳本動 → 一定是控制層或手臂問題，與訊號無關。
直接上真訊號的話，手臂不動你分不清是分類錯、串列掉包、還是手臂連線問題。

**mock 腳本內容**（`sources.py`，會循環）：

```
2.0s rest → 2.0s index → 2.0s thumb → 1.5s pinch → 1.5s rest → 1.5s pinch
→ 2.0s elbow_flex → 2.0s shoulder_flex → 2.5s pinch+elbow → 2.0s rest
```

### 6.4 絕對不要做的事

- ❌ **不要寫第二份前處理實作。** `preprocess.StreamFilter` 是唯一實作，
  離線 `filter_causal()` 就是把整段餵給它，已驗證逐位元相同。
  訓練與推論的前處理只要有一點差異，準確率就會崩。
- ❌ **不要改 SPI prescaler。** `SPI_BAUDRATEPRESCALER_16` → SCLK 1 MHz 是
  硬性需求：27 bytes = 216 µs 必須塞進 2 kSPS 的 500 µs DRDY 週期。
  改成 64（250 kHz）會變成 864 µs，**每個 sample 都 overrun**。
- ❌ **不要混用不同來源的校準區段。** 訓練與推論的尺度來源必須相同，
  混用會讓全對率從 99.6% 掉到 58%（實測）。
- ❌ **不要在 CubeMX 重生成前忘記備份 USER CODE 區塊。**

## 8. 🎬 上機測試影片拍攝計畫

建議三段，總長控制在 2–3 分鐘：

### (a) 單一自由度各一次

```
elbow_flex     → J3 從 180° 移到 90°
shoulder_flex  → J2 從 −90° 移到 0°
pinch          → 夾爪 CLOSE，再捏一次 → OPEN（toggle 是最有說服力的一段）
```

每個動作做完回中性，讓觀眾看清楚對應關係。

### (b) 複合姿勢

```
pick_and_raise  = 捏住 + 彎肘 + 前舉（三個 DOF 同時）
```

證明是**多輸出**而非單一多類分類 —— 這是本專案架構的核心賣點。

### (c) 螢幕錄影同框

終端機的即時預測輸出 + 手臂畫面放在同一個畫面：

```
[ARMED   ] hand=pinch (0.94) elbow=flex (0.88) shoulder=rest (0.91) | J2=-90.0 J3=134.2 J6=+12.0 | grip=CLOSED | cmdnum=1
```

這一段同時展示了信心值、目標角、夾爪狀態，資訊密度最高，適合放海報的 QR code 連結。

### 拍攝注意

- **手臂全程懸空**（見 §5.5），否則畫面上會出現「使用者放鬆 → 手臂自己回 home」的尷尬畫面
- 開場先拍 5 秒校準期（保持中性放鬆），順便交代協定
- 建議準備兩個機位或分兩次拍：一次拍人、一次拍手臂，後製並排
